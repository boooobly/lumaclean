## Арифметика

1. Сложить сырую стоимость площади и выбранных допработ.
2. Применить минимум заказа как floor, а не дополнительный сбор. При химчистке ADDON второго минимума нет.
3. При срочности **или** согласованном празднике применить одну надбавку 20%. Совпадение не даёт 40%.
4. Только при выбранной crypto оплате добавить 5% после service surcharge; ×1.20×1.05=×1.26.
5. Итоговую смету RSD округлить вверх до 100 один раз. Согласованные прежние цены/скидки/snapshots задним числом не пересчитывать.

## Предлагаемые длительности

### Предложение длительности для двух исполнителей — НЕ АКТИВИРОВАНО

Источник труда — J листа 01; это человеко-минуты. Деление на два даёт только идеальную нижнюю границу при полной параллельности. Владелец подтвердил на **50 м²**: regular **120 минут**, deep **360 минут elapsed**, команда 2, обычное загрязнение, без extras и дороги. Поэтому предложения для остальных bands масштабированы относительно этих точек: regular `ceil5(труд × 120/220)`, deep `ceil5(труд × 360/480)`. Линейная пропорция — открытое допущение для обсуждения, не утверждённый норматив остальных площадей. В БД предложения не активировались.

Все дополнения, кроме духовки, пока предложения из Sheet. Engine складывает минуты дополнений последовательно и умножает их на количество; на число клинеров не делит. Две духовки требуют 90 чел.-мин; 45 elapsed достижимы только если два свободных исполнителя действительно работают параллельно. Текущий консервативный расчёт добавит 90 elapsed. Автоматический поиск «критического пути» работ в существующей архитектуре не реализован и не имитируется делением всех строк пополам.

Ожидание цикла стиральной машины может перекрываться с уборкой; полный цикл нельзя автоматически прибавлять к активному труду или повторно тарифицировать включённую загрузку deep. Если сдача объекта требует окончания цикла, длительность определяется позднейшим завершением обязательной работы.

Календарь считает конец работ отдельно от `cleaningReserveMinutes`. Между заказами нужны: резерв предыдущей уборки + **один** `max(defaultTravelBufferMinutes, buffer A, buffer B)` + проверенная дорога (либо отдельный согласованный fallback). Буферы двух заказов не суммируются. 30 минут резерва не подменяют дорогу и не должны повторно попадать в `baseMinutes`.

Два эмпирических значения получены и повторно не запрашиваются. Для полного диапазона AUTO ещё нужен выбор владельца: утвердить предложенные остальные bands после хронометража либо ограничить canary подтверждёнными 50 м² и передавать остальные площади человеку. Неизвестные extras и особые работы продолжают блокировать автоматическую запись.

## Контроль версий

- Перед каждым release получить свежие read-only ranges 01–06; зафиксировать дату, точные ranges, sourceHash и компактный контракт. Изменение Sheet требует review diff по **цене, единице, статусу, scope и inclusion**, а не только хэша.
- CI сравнивает approved contract с runtime и knowledge. Обновлять fixture одновременно с кодом без owner review нельзя; raw Sheet export хранить вне публичного Git.
- `sync-business-knowledge.ts` принимает шесть bounded tabs и ограничивает auto capabilities пятью реализованными пакетами. Новые aliases не становятся услугами автоматически. Стабильные исходные code сохраняются.
- DB tariff update — отдельный reviewable dry-run, новая validFrom/version, закрытие прежних bands; без изменений negotiated prices, payouts, historical records. В этом аудите update script не запускался на production.
- После изменения source нужны pricing/unit/HTTP/browser QA, новое source-bound evidence и native/live gates. Хэш успешного manual-only build не даёт разрешения включить AUTO.
- Offline CI не узнаёт о самостоятельной правке Sheet до нового export: автоматический read-only freshness probe можно подключить только после выбора владельцем credentials/периодичности/получателя. Такое слепое пятно явно остаётся, а не скрывается словом «синхронизация».
