# LumaClean Admin — планирование

Этап `codex/admin-scheduling`, база `codex/admin-crm-core`. Реестры Leads → Clients → Orders и публичный pricing сохранены. Планирование использует `Order`, существующие `CleanerAvailability` и `OrderCleaner`.

## Интерфейс

`/admin/cleaners`: поиск, страницы реестра, профиль, создание/редактирование, активация, транспорт, языки/навыки, рейтинг, заметки и nullable процент. Адрес без координат. Недельный график — weekday 1–7 и локальные минуты, включая регулярные выходные. Особые часы заменяют недельный интервал на дату; полная или частичная недоступность требует подтверждения при назначении.

`/admin/calendar`: неделя по умолчанию, день, месяц (42 календарные ячейки), фильтр клинера и таблица распределения по команде. Использован собственный React слой и HTML drag/drop: установленные React 19.2.4 / Next.js 16.3.8, без calendar dependency, платных resource plugins или несовместимых peer dependencies. Chrome проверен реальным перемещением мышью. На телефоне неделя/день показываются как agenda с выбором даты; назначения и время меняются в доступном native dialog с Escape и удержанием фокуса. Resize заменён быстрыми кнопками 60/90/120/150/180 минут и произвольным вводом.

Слот открывает существующую форму Order с датой/временем, без дублирования CRM. Карточка и dialog показывают услугу, клиента, адрес, время, длительность, состав/численность команды и текстовый статус. Завершённые/отменённые/неявки доступны для просмотра. Закрытые неразмещённые окна вынесены из списка ожидающих размещения. Dashboard показывает компактный сегодняшний список и текущие предупреждения с переходом в полный календарь.

## Время и правила

Business zone: **Europe/Belgrade**. Начало и клиентское окно хранятся как timestamptz; рабочие часы как weekday/date + local minutes. Неоднозначное/несуществующее время ручного начала на DST отклоняется. Для границ рабочего интервала начальная неоднозначность выбирает первое вхождение, конечная — последнее; отсутствующая граница сдвигается вперёд. Это явно расширяет доступный рабочий период, а длительность уборки остаётся фактически прошедшими минутами.

Длительность: `manualDurationMinutes ?? estimatedDurationMinutes`, без формулы по площади. При неизвестной длительности конец отсутствует и проверка пересечений неполна. Такой FIXED заказ требует подтверждения предупреждения при изменении; размещение FLEXIBLE без длительности запрещено. FLEXIBLE до размещения остаётся без start, после размещения сохраняет оба promised window timestamps; вся уборка обязана попадать в окно. Снятие с календаря очищает start/end, сохраняя окно и назначения.

`SchedulingConflictService` — единый domain service для календаря, команды и существующего CRM edit:

- **ERROR**: пересечение одного клинера с другой уборкой (включая cleaning reserve), выход FLEXIBLE за окно, размещение FLEXIBLE с неизвестной длительностью. ERROR нельзя подтвердить.
- **WARNING**: нехватка клинеров, незаданный график/длительность, рабочие часы/выходной/исключение, сохранённое назначение неактивного клинера, недостаточный операционный промежуток. Подтверждение требует актуальных ключей всех предупреждений и объяснения минимум 5 символов.
- CANCELLED/NO_SHOW не блокируют время. DRAFT с назначениями блокирует, COMPLETED сохраняет историческую занятость. Неактивный клинер сохраняет старое назначение, но не получает новое.
- Между уборками учитывается максимум 30 минут и сохранённых буферов обоих заказов, отдельно от cleaning reserve. **Дорога не проверена**: буфер не гарантирует возможность поездки. Google Maps/Routes, общественный транспорт, маршрутизация и оптимизация не реализованы.

Изменение графика не переписывает назначенные заказы: календарь и карточка показывают возникшие предупреждения, владелец решает, перенести ли работу. Подтверждения сохраняются как история решения; они не скрывают текущий риск. Ключи предупреждений включают дату/длительность/участников и отпечаток текущего текста, поэтому подтверждение другого количества людей или другой даты не подходит.

## Запись, авторизация и аудит

Все команды проходят strict Zod, текущую активную ADMIN роль, exact Origin/JSON и ограничение тела. Проверка + Order + назначения + override + аудит выполняются в одной PostgreSQL transaction. Advisory locks: общий существующий ключ `order:<id>`, затем отсортированные `scheduling:cleaner:<id>`. Графики/активность используют тот же cleaner lock. Конкурирующие заказы одного человека сериализуются и повторно проверяют актуальные записи. `expectedUpdatedAt` защищает быстрый редактор от устаревших изменений.

Drag не меняет карточку оптимистически: серверная ошибка оставляет прежнее положение, dialog показывает предложенное время/конфликт. После успеха повторно запрашивается тот же ограниченный период. При потере ответа интерфейс просит обновить данные — не обещает откат уже совершённой транзакции. Чтение не пишет аудит; сохранение неизменённого плана тоже. Контакты и заметки клинеров не копируются в AuditLog. Причина override хранится в отдельной защищённой `SchedulingOverride`.

## Миграция и запросы

`20261001150000_admin_scheduling` — additive: nullable `Order.scheduledEnd`, nullable `OrderCleaner.removedAt` (снятие сохраняет историческую строку), `SchedulingOverride` и FK/CHECK, разрешение null weekly period для регулярного выходного. SQL trigger вычисляет end из выбранной существующей длительности при каждом Order insert/update и backfill; elapsed минуты добавляются в UTC даже при другом timezone соединения. Длительность не угадывается. Добавлен индекс end для ограниченных interval queries. Старые поля/назначения/часы сохранены.

API принимает только day/week/month и валидную дату, не произвольный исторический диапазон. Запрашивает выбранные 1/7/42 дня, плюс одни соседние сутки для проверок промежутков/переходящих уборок. Максимум 1000 заказов, 200 активных клинеров с явным индикатором предела; необходимые исторически назначенные клинеры добавляются отдельно. При превышении 1000 связанных заказов командная проверка прекращает запись, а не принимает непроверенный план. Availability читается только weekly и исключения нужного диапазона. Карточка клинера показывает недельный график и последние 150 исключений; более старую дату можно заменить через форму. Полная история изменений — в БД, UI истории показывает последние 50 событий.

Нынешняя выборка соседних заказов рассчитана на операционный буфер/резерв менее суток (текущий default 30/0, редактирование этих параметров на этом этапе закрыто). Если будущий этап позволит буферы/резервы свыше суток, расширить interval query по реальному busy end до открытия такой настройки. Для маршрутов потребуется provider/cache и новые логистические проверки; существующий domain service и блокировки остаются точкой записи.
